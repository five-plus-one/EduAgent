# 多模态AI互动式教学智能体 - 后端技术栈与架构选型答辩备忘录

为了应对比赛评委可能的提问，特准备此文档记录核心技术选型背后的思考：为什么我们选择这套配置？这套配置对系统、对客户（教师）有什么不可替代的好处？

---

## 1. 为什么后端选用 Python + FastAPI 组合？

### 🎤 答辩要点（对内技术视角）：
- **Python 是 AI 生态的绝对核心**：项目强依赖大模型（LLM）调用、RAG 向量检索和多模态文件解析（如 PDF 提取、Word 与 PPT 的生成）。在 Python 环境下，我们可以直接使用 `LangChain`, `python-pptx`, `PyPDF2` 等成熟生态，开发效率远超 Java 或 Node.js。
- **FastAPI 原生支持异步与流式响应**：FastAPI 构建于 ASGI 标准之上，具有极高的异步并发性能。本项目最核心的体感体验是“类似 ChatGPT 的打字机输出结果”，也就是 Server-Sent Events (SSE)。FastAPI 配合 `StreamingResponse` 能极其优雅、稳定地实现流式对话体验。

### 🎤 答辩要点（对外客户视角）：
- **“所见即所得”的极速响应**：基于 FastAPI 的高性能异步处理，当教师输入一段改写指令时，服务器可以毫无等待地把大模型的每一个推导字“实时流式”投影到前端界面上。减少了“黑盒等待焦虑”，极大提升了交互沉浸感。

---

## 2. 为什么直接调用大模型 API (Doubao & Text-Embedding) 而不是自研/本地化部署小模型？

### 🎤 答辩要点：
- **保证自然语言理解的“深层逻辑还原”**：教育领域的意图理解（比如把一页散漫的备注要求，提炼为具有起承转合的严密教学大纲）极其依赖模型的涌现能力和参数体量。使用参数规模庞大且经过深度优化的头部模型（如豆包），能够避免小模型经常出现的“幻觉”、“逻辑断层”和“格式不服从”问题。
- **免维护、高可用的开箱即用**：采用 API 接入可以大大减低项目后期的算力运维难度。我们不需要昂贵的 GPU 显卡服务器，任何一台普通的 CPU 电脑就可以跑起整个后端系统，有利于该产品的低成本推广和私有化轻量部署。

---

## 3. 为什么在项目初期使用 SQLite 作为数据库？后期如何扩展？

### 🎤 答辩要点：
- **无须外部依赖的敏捷落地**：由于比赛或 MVP (最小可行性产品) 阶段演示环境多变，且要求“不添加庞大的外部依赖”，SQLite 是一个极其纯粹的嵌入式文件数据库。它不需要在客户/评委的机器上安装服务器软件或配置环境变量，项目克隆下来双击就能直接跑起来，非常“防身”。
- **无缝平滑的架构演进**：由于我们在代码中使用了 **SQLAlchemy (ORM 框架)** 把所有的 SQL 语句都做了对象化封装。这就意味我们的业务逻辑是完全“不认数据库种类”的。如果后期产品正式交付给学校的百人教师群体，面对高并发读写，我们连一行核心代码都不用改，只需把连接字符串从 `sqlite:///xxx.db` 修改为 `mysql://xx:xx@host/db` 就可以瞬间无缝切换到企业级的 MySQL 上。这展示了我们**优秀的系统架构扩展性**。

---

## 4. 如何保证项目最核心的“多模态文件解析 + JSON 渲染 PPT”的稳定性？

### 🎤 答辩要点：
- 我们没有采用大模型直接裸写二进制文件（容易导致文件损坏）的不可控方案。
- 我们采用了**大模型+确定性逻辑双轨制**这一目前最佳落地实践：
  1. 通过 RAG 切片和 Embedding 模型将文档转化为特征库，供大模型寻找灵感。
  2. 大模型**只负责输出结构化的 JSON 数据（明确定义了每页的 Title、Bullets 和版式）**，并通过 `Pydantic` 进行严格的字段校验。
  3. JSON 回到后端引擎后，由 `python-pptx` 这类纯物理逻辑的脚本按照预设的排版对齐方式，精准“拼装”出 `.pptx` 课件，做到了“智能感”与“100%可控性”的完美统一。

---

## 5. 为什么在文档资料库解析 (RAG) 中引入 ChromaDB 与后台异步队列 (BackgroundTasks)？

### 🎤 答辩要点：
- **引入 ChromaDB 是为了做“精准外脑”**：传统数据库只能根据关键字搜索，而 ChromaDB 是**向量数据库**。它配合 `text-embedding-3-large` 大模型将教师长达几百页的教案通过数学高维向量表征“语义”。这就意味着即使用户搜索或质问时没有用一模一样的汉字字眼，大模型也能在大海捞针中根据“意思贴近”查出那一段段精确的文档切片片段（Chunk）。
- **后台异步化 (BackgroundTasks) 最大限度地消除了前端卡顿阻塞**：由于提取 PDF 文字和调用大模型转化为成千上万维的浮点数组需要耗费极严重的算力与时间，我们在 FastApi 中使用了**线程旁路作业**。也就是说，前端只要把文件顺着网线抵达了服务器，接口 `1毫秒` 内就会响应成功 `{"status": "processing"}` 而不被卡死。沉重繁杂的解析过程自动下放进入隐形的多线程队列中缓慢执行，而前端仅用微小的数据包定期轮询获取进度值，这是现代化高并发系统的标配作风（体现了我们的工程素养）。
